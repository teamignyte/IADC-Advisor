# For Liam — how this bundle was built and why

This is the maintainer's-eye view of the Appian architect-in-a-box: what it's for, the decisions behind its shape, what actually got built, and the one piece that was deliberately deferred. (`README.md` is the user-facing version and, unlike this file, presents everything as built.)

## Purpose

A **reusable Claude Code bundle** that configures Claude as an **advisory Appian architect** — it interrogates/sharpens dev planning, answers questions about an Appian application, and produces specs and ticket breakdowns, for both architects and onboarding developers. It explicitly **does not execute development**: no writing code, no building Appian objects. It advises, plans, and hands off.

It's a **template**: every adopter re-points it at their own Appian project via `/setup`. The graph MCP builds a graph for *any* Appian application; the `jira` skill works against any project key; IADC-specific values became placeholders.

## Decisions we made (and why)

1. **Scope: reusable template, not IADC-specific.** The `iadc` graph service builds graphs for any Appian app (the name is the product, not the app). The Jira skill works against any project key (read from `docs/agents/issue-tracker.md`).
2. **Skill boundary: "through work-breakdown."** Kept interrogation + design + backlog creation (interrogate-*, domain-modeling, to-spec, to-tickets, setup). **Cut the code-writing skills** (`implement`, `tdd`, `code-review`) — those are execution. **`triage` was also cut** during the review pass: its load-bearing moves (reproduce bugs, run tests, drive a Jira state machine, write briefs for AFK execution agents) all clash with the advisory / no-execution / human-first-Jira posture, and what remained overlapped `interrogate` + `jira` (read). Its `AGENT-BRIEF.md` / `OUT-OF-SCOPE.md` went with it. The readiness-label vocabulary (`triage-labels.md`) stays — `to-tickets` applies `ready-for-agent` and `jira` reads the labels.
3. **Appian MCP posture: read-only / advisory.** Configured with `LCP_TOOL_MODE=readonly`, which exposes only `list*`/`get*` and drops all mutating tools — and note it **also drops the environment-touching test/validate tools**, so it's effectively GET-only (slightly stricter than "read-only but validate/test allowed"). The `appian` skill's create/update material is reframed as advisory reference.
4. **Jira posture: human-first, read-mostly, light gated writes.** Unlike the original IADC app (where the agent had wide-ranging board control), this client treats Jira as human-first: the architect *reads* the board freely via the Jira MCP and does at most light, gated writes (a label, a comment, a status transition) — every write proposed first, confirmed, then verified by re-read. All Jira access is through the **Jira MCP connector** — no REST API, no `acli`, no tokens (dropped for consistency per a later instruction: enforce MCP, don't mention CLI/REST). Consequence: the old `jira-hygiene` skill was first slimmed from a 450-line REST audit engine to an MCP-driven advisory, then — on further direction that its real job is *context for the Appian advisor, not board cleanup* — reduced again and **renamed to `jira`**: a read-mostly "read the board for context + optional light comments" skill (its `audit.ps1`/`selftest.ps1` scripts were removed, and the detection-catalog/auto-fix framing dropped entirely). Board cleanup is now a human job. The MCP's inability to delete issue links is now only a minor caveat — only `to-tickets` creates links (dependency `Blocks`), and a wrong one is fixed by a human, not the agent (the `issue-tracker-jira.md` seed notes this).
5. **Office/SharePoint role: read docs + collaboration** (SharePoint/OneDrive + Teams/Outlook, read-only) — **but not built** (see below).
6. **First-run: a guided `/setup` skill** (rather than a manual README checklist). It also absorbed the old tracker/label/domain-doc setup and now does MCP wiring + a connectivity/validation pass. Because the bundle is Jira-first and the upstream setup skill only shipped GitHub/GitLab/local seeds, we added a **`setup/issue-tracker-jira.md` seed** — adapted from the IADC project's own `docs/agents/issue-tracker.md` (the convention doc the tracker skills point at). It keeps the reusable conventions (board model, issue format, ADF gotchas, operation→**MCP-tool** table, Wayfinding operations) with `<PLACEHOLDER>`s, rewritten so all Jira access is through the **Jira MCP** (no REST/CLI — see decision #4), and demotes IADC's specific workstream labels (its "layer/phase" axis) to a *replace-me example* of the generic "workstream label axis". `/setup` fills it into a live `docs/agents/issue-tracker.md` per adopter — so no project-specific tracker doc is committed to the template.
7. **Anonymization + rename.** Removed all "Matt Pocock" / `ask-matt` / aihero branding. Renamed the `grill` family to `interrogate` everywhere: `grilling→interrogating`, `grill-me→interrogate-me`, `grill-with-docs→interrogate-with-docs`, and every reference/trigger. `setup-matt-pocock-skills→setup`; `ask-matt→which-skill`.
8. **Added skills:** `research`, `handoff`, `teach`, `wayfinder`, and `which-skill` (the anonymized, de-referenced router). Each was checked for transitive deps.
   - **wayfinder** referenced `/prototype` (which writes+runs throwaway code). We **skipped `/prototype`** and adapted wayfinder's `prototype` ticket type to mean a *non-code* rough artifact (outline/stub/mock), so it stays execution-free.
   - We evaluated the whole **superpowers** plugin and the Anthropic skills for inclusion; **none made the cut** — the execution ones conflict with "no execution," and the planning-adjacent ones (`brainstorming`, `writing-plans`) substantially overlap `interrogate-*`/`to-spec`/`to-tickets`.
9. **MCP config: `iadc` + `appian` (readonly) + `context7` in `.mcp.json`** (literal values, gitignored — see #11 for why not `${VAR}`); **Jira stays a Claude connector** (OAuth, can't live cleanly in a committed file); Office/SharePoint not present.
10. **context7 vs docs.appian.com — keep both.** context7 is the fast semantic **discovery** layer (its Appian index is a subset, pinned to an indexed version that may lag the environment); `docs.appian.com` at the project's version is the **authority**. The `context7` skill encodes: search context7 first, confirm version-sensitive answers against docs.appian.com.
11. **Secrets: literal gitignored `.mcp.json` + committed `.mcp.json.example`.** We first planned `${VAR}` expansion in a committed `.mcp.json` (values in a gitignored `.env`). Checking the Claude Code docs killed that: `.mcp.json` `${VAR}` expansion reads only the **OS/shell process environment** (a `settings.json` `env` block is **not** confirmed to feed it — cf. open feature-request #46889), and — decisive here — the **Windows Desktop app has a bug (#40372) where it doesn't expand `${VAR}` in a `.mcp.json` `env` block at all**. This project runs on the Desktop app and the `appian` server's `env` block holds the password, so expansion was the exact thing that would silently fail. So the real **`.mcp.json` holds literal values and is gitignored**; a committed **`.mcp.json.example`** carries placeholders. Literal values dodge the expansion bug entirely and still keep secrets out of git. There are **no other secret files** — `.env`/`.secrets/` were removed once the Jira REST hygiene path was dropped (decision #4); the Jira MCP connector needs no local tokens, so the gitignored `.mcp.json` is the only secret-bearing file.
12. **`/run-skill-generator` was N/A.** This bundle has no launchable app — the "product" is Claude configured by these files. Rather than fabricate a driver, the meaningful analog (does `.mcp.json` parse, do the MCPs handshake, is skill frontmatter valid) was folded into `/setup`'s verification step.

## What got built

- **Skills** (`.claude/skills/`, 17): `interrogating`, `interrogate-me`, `interrogate-with-docs`, `domain-modeling`, `to-spec`, `to-tickets`, `wayfinder`, `research`, `handoff`, `teach`, `which-skill`, `setup`, `appian`, `iadc-graph`, `jira`, `context7`, and `office` (placeholder).
- **`.mcp.json`** — `iadc`, `appian` (readonly), `context7`, literal values, gitignored; committed `.mcp.json.example` carries placeholders.
- **Secrets scaffolding** — gitignored real `.mcp.json` (the only secret-bearing file); committed `.mcp.json.example` + `.gitignore`.
- **Docs** — this file, `README.md`, and the rewritten `CLAUDE.md`. `/setup` generates `docs/agents/*.md` per project.

## NOT built: the Office / SharePoint MCP + skill

**Deferred deliberately.** There is **no Office/SharePoint MCP connected**, and the `office` skill is a **stub placeholder** that tells the agent the capability doesn't exist. The design intent (read-only SharePoint/OneDrive docs + Teams/Outlook context) is recorded in `.claude/skills/office/SKILL.md`.

To finish it:
1. Pick and connect a Microsoft 365 / SharePoint MCP server (Microsoft Graph-based), wired into `.mcp.json` with read scopes and literal secrets like the others (and a placeholder entry in `.mcp.json.example`).
2. Replace the `office` stub with a real skill (tool names, auth/permission model, how to locate a site/drive/document, read-only usage patterns).
3. Add it to `.mcp.json`, route to it from `CLAUDE.md` and `which-skill`, and delete this "NOT built" section.

## Extending the bundle

Use the **`skill-creator`** skill (available in this environment) to author or edit skills — it carries the frontmatter conventions, progressive-disclosure structure, and description-triggering guidance, and it can run eval loops to harden a new skill. When you add or rename a skill, update `which-skill` (the router) and the skill map in `CLAUDE.md` to match.
