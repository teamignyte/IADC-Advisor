# The deliverable ships as a Claude Code plugin (`iadc-advisor`)

The product now ships as a Claude Code **plugin** named `iadc-advisor`, distributed from
this repo acting as its own private **marketplace** (`.claude-plugin/marketplace.json` at
the root points at the plugin folder). Clients declare **both** the marketplace and the plugin
at **project scope** — once per Appian-app repo, in that repo's committed
`.claude/settings.json`, so a teammate who clones it can resolve the plugin.
This supersedes the flatten-into-repo install: nothing is copied into the client repo by
hand anymore, and updates arrive by bumping `version` in `plugin.json` (deliberate
releases + `CHANGELOG.md`, never per-commit).

Driver: distribution and updates. The product stays conceptually **per-Appian-application**
— one app repo per application; the plugin is only the delivery vehicle.

Plugins cannot ship a loaded `CLAUDE.md`, so the operating posture moves to a
**SessionStart hook** that injects it, along with the project's configuration files
(`docs/agents/project.md`, overridden per-person by the gitignored
`docs/agents/project.local.md` — how a lead and a developer share one repo seamlessly).

MCP servers stay in a project-level gitignored `.mcp.json` generated by `/setup` from a
template that rides inside the plugin: the servers span per-app (`LCP_URL`, graph URL),
per-person (Appian credentials), and per-machine (`uv` path) values, which no
plugin-manifest mechanism (`userConfig` is plugin-wide per machine) can express — and the
docs explicitly steer self-hosted stdio servers to project `.mcp.json`.

## Considered options

- **Direct git install, no marketplace.** Rejected: loses update/versioning ergonomics
  and room for future plugins.
- **Separate marketplace repo.** Rejected: a second repo to maintain, for one plugin.
- **MCP servers in the plugin manifest via `userConfig`.** Rejected: wrong granularity
  (one value per machine across all apps) and re-risks the Windows `${VAR}` expansion bug
  that literal `.mcp.json` values were chosen to avoid. Future note: if the `iadc` graph
  is ever centrally hosted behind OAuth, it graduates into the manifest as a remote HTTP
  server — the ecosystem-preferred pattern.
- **User-scope install.** Rejected: the posture hook would fire in every unrelated project.

## Consequences

- ADR 0001's shipping story is amended: "only `deliverable/` ships" becomes "only the
  plugin folder ships", enforced by the marketplace `source` rather than by copying. The
  folder is renamed `iadc-advisor/`.
- `/setup` becomes the materializer of all per-project state (see ADR 0010): it writes
  `.mcp.json`, `docs/agents/*.md`, `.gitignore` entries, and `outputs/` into the app repo.
- Dogfooding changes: instead of opening Claude in the plugin folder, install the plugin
  from a local-path marketplace into a scratch client repo.
- No migration path: no flattened installs exist (clean break).
- **The manifest must stay minimal — never declare `skills` or `hooks` in
  `iadc-advisor/.claude-plugin/plugin.json`.** Both are auto-discovered from `skills/` and
  `hooks/hooks.json`; declaring them *additionally* registers the same paths twice, and the
  plugin then **installs successfully but loads nothing** — `✘ failed to load — Duplicate hooks
  file detected`, no skills, no posture hook. It fails silently in the worst place: **`claude
  plugin validate` passes on the broken manifest**, so validation is not a gate. The only check
  that catches it is a real install reporting the plugin as `enabled` in `claude plugin list` —
  which is therefore the release check, not `validate`.
